# ARP 

**Indicators of Attack**
1. Duplicate MAC-to-IP mappings 
2. Unsolicited ARP replies 
3. Abnormal ARP traffic volume
4. Unusual Traffic Routing
5. Gateway redirection patterns 
6. ARP Probe/Reply loops  - Many ARP requests with `Who has 192.168.1.x? Tell 192.168.1.y` patterns.
Let's say we have a router 192.168.10.1, since routers are mainly used for ARP poisoning for on-path attacks, we can isolate it by knowing what devices are trying to pretend to be the gateway. We can do this by filtering: 

Assuming that this is the IP of the router. 

```
arp.src.proto_ipv4 == 192.168.10.1 and arp.opcode == 2
``` 

 This shows hosts that are responding that 192.168.10.1 is them. This can be tied with the MAC address, which can be identified if there are any duplicates. 

After knowing if there are any duplicates we can get the:
1. MAC address of the attacker 
2. IP address tied to that MAC address within the network
and then after that we can correlate 

We can add filters like 
`eth.addr == "attacker mac"` - this is now layer 3, and we can check if there are any active communications tied with the attacker's MAC address along with IP addresses that aren't mapped to that MAC

# DNS Spoofing

or DNS Cache Poisoning corrupts the system, by giving the computer the wrong address of the website you are trying to visit. 

The process of how it works:
1. Victim tries to visit bank.com
2. Attacker, who is already on the local network (perhaps by ARP Spoofing), intercepts the DNS query 
3. The attacker quickly sends a fake DNS response to the victim. This fake response says, bank.com it at my IP address:**ATTACKER_IP**
4. The interception: The victim's computer trusts the response and saves it locally to its cache. When the victim tries to connect to the bank, the victim unknowingly connects to the attacker's server, which might host a perfect replica of the bank site.

**Indicators of Attack**
1. Multiple DNS responses for the same query: 
```
Victim → DNS query: What is bank.com?  Transaction ID: 0x1234

Attacker → Fake response: bank.com = ATTACKER_IP
Resolver → Real response: bank.com = REAL_BANK_IP
```
A useful workflow is to select the query, note its `dns.id`, and filter:

**WIRESHARK**
```
dns.id == 0x1234
```

2. DNS response from an unexpected source: 

```
192.168.1.20 → 192.168.1.1   DNS query:    What is bank.com?

192.168.1.50 → 192.168.1.20  DNS response: bank.com = ATTACKER_IP
192.168.1.1  → 192.168.1.20  DNS response: bank.com = REAL_BANK_IP
```
```
Query was sent to:       192.168.1.1
Response came from:      192.168.1.50
```

Can be spoofed though

To check we can use this command: **WIRESHARK**
```
dns.flags.response == 1 &&
ip.dst == 192.168.1.20 &&
ip.src != 192.168.1.1
```
It shows responses that are headed to the client, but isn't coming from the real DNS resolver

3.  **Suspiciously short TTL (Time-To-Live) values**: Attackers use very low TTLs (1 - 30s) to keep poisoned entries short-lived and reassert control.

```
bank.com = 203.0.113.10
TTL = 300 seconds

The answer can be cached for 5 minutes.
```

```
bank.com = ATTACKER_IP
TTL = 5 seconds

After 5 seconds:
Cache entry expires
        ↓
Victim sends another DNS query
        ↓
Attacker sends another forged response
```

**WIRESHARK**
```
dns.flags.response == 1 && dns.resp.ttl <= 30
```

4. **Unsolicited DNS responses**: A DNS reply appears without a corresponding DNS request from the victim.
**Wireshark**
```
dns.flags.response == 1 && !dns.response_to
```

means:

```
Show DNS responses
AND
Wireshark found no matching earlier request
```

Workflow
```
1. Is the alleged responder an approved DNS resolver?
2. Did two responses actually refer to the same query?
3. Were the returned addresses genuinely conflicting?
4. Which response arrived first?
5. Did the victim connect to the suspicious returned address?
6. Are there ARP changes involving the gateway or resolver?
7. Did DHCP, VPN software, or endpoint settings change the DNS server?
8. Did other systems receive the same malicious answer?
```

```
dns.flags.response == 1 
```

Filtering in legitimate traffic, IP address is from the legitimate DNS resolver. If there are conflicting IP addresses, we can always check out our inventory for it 

Finding our conflicting IP we can check the domain 
```
dns && dns.qry.name == "corp-login.acme-corp.local"
```

```
dns.flags.response == 1/0 for requests &&
ip.dst == 192.168.1.20 &&
ip.src != 192.168.1.1
```

Basically checks responses headed to client but it shows responses that are not from the DNS resolver 

```
1. Who asked?       Victim IP and hostname
2. Who was asked?   Destination resolver IP
3. Who answered?    Response source IP and relevant source MAC
4. What was given?  Returned dns.a/dns.aaaa address and TTL

```

# SSL Stripping in Action 
On-path technique which aims to remove/prevent TLS encryption between a client and a server. 
The **attacker retains a secure (HTTPS) session with the server** while r**elaying plain HTTP to the victim, enabling eavesdropping and credential capture.**

Assume:

```
Victim:   192.168.1.20
Attacker: 192.168.1.50
Bank:     203.0.113.10
```

**1. Attacker becomes MITM**

The attacker uses ARP spoofing or a rogue access point:

```
Victim → Attacker → Router → Internet
```

**2. Victim begins with HTTP**

Perhaps the victim enters:

```
bank.com and then the browser attempts GET / HTTP.1.1 
```

This is what happens over the network
```
Victim → bank.com:80
TCP handshake
HTTP GET /
```

**3. The real bank requires HTTPS**

Normally, the bank would respond:

```
HTTP/1.1 301 Moved Permanently
Location: https://bank.com/
```

**4. Attacker removes the upgrade**

Instead of forwarding the redirect normally, the attacker keeps the victim on HTTP:

```
HTTP/1.1 200 OK
Content-Type: text/html

<a href="http://bank.com/login">Log in</a>
```
```
http://bank.com/login (mighte rewritten the response even if it was /)
```

**5. Attacker creates a separate HTTPS connection**

The attacker now connects to the real bank:

```
Attacker → Bank:443
TCP handshake
TLS handshake
Encrypted HTTP traffic
```
**6. Victim submits credentials**

The victim sees the bank’s content, but their connection is still HTTP:

```
POST /login HTTP/1.1
Host: bank.com
Content-Type: application/x-www-form-urlencoded

username=<user>&password=<redacted>
```

The attacker then forwards the request through their encrypted connection:

```
Victim → Attacker:
Plain HTTP credentials

Attacker → Bank:
Same credentials protected by TLS
```

In Wireshark, depending on where you capture, you might see:

```
Victim side:

ARP poisoning activity
TCP port 80
HTTP GET and POST requests
Readable credentials, cookies and content
```

Workflow of it: 
```
1. Victim requests http://bank.com/ but modern browsers don't usually allow http
2. Attacker requests https://bank.com/
3. Bank returns its real HTML to the attacker.
4. Attacker decrypts it because they are one endpoint of that TLS session.
5. Attacker changes HTTPS links to HTTP.
6. Attacker sends the modified HTML to the victim.
```
ALL AUTOMATED 
```
Victim’s request:
username=<user>&password=<redacted>
        ↓
Attacker’s proxy reads it
        ↓
Proxy submits the same information to the bank
        ↓
TLS software automatically encrypts it during transmission
```

The bank’s response travels in the opposite direction:

```
Bank encrypts response for attacker
        ↓
Attacker’s TLS software automatically decrypts it
        ↓
Proxy reads or modifies the response
        ↓
Proxy sends it to victim as plaintext HTTP
```

**Indicators of SSL Stripping**
1. Initial request might be for HTTPS port 443, but the subsequent packets immediately shift to unencrypted HTTP port 80
2. Redirects/Link rewriting: Monitoring for redirects (HTTP status code 301, 302) persistently to a http resource 
3. Certificate errors: Initial handshake might contain self-signed certificate 
### Wireshark Investigation

**For a known victim:**

```
ip.addr == 192.168.1.20 &&
(tcp.port == 80 || tcp.port == 443)
```
**Compare TLS and HTTP traffic for the same domain:**

```
tls.handshake.extensions_server_name == "bank.com" ||
http.host == "bank.com"
```

**Look for failed or reset 443 connections:**

```
ip.addr == 192.168.1.20 &&
tcp.port == 443 &&
tcp.flags.reset == 1
```
**Look for sensitive POST requests over HTTP:**

```
http.request.method == "POST" &&
http.host == "bank.com" &&
tcp.port == 80
```

For DNS Poisoning 
```
Victim requests:
Host: bank.com
GET /login
        ↓
Attacker’s proxy recognizes bank.com
        ↓
Proxy opens HTTPS connection to real bank.com
        ↓
Proxy forwards GET /login
```

For ARP Poisoning 
```
Receive victim’s HTTP request
Read Host, path, headers and submitted data
Create equivalent HTTPS request to real website
Receive and decrypt bank’s HTTPS response
Rewrite HTTPS references when necessary
Send plaintext HTTP response to victim
```

```
Who connected?
Victim IP, hostname, user and asset importance

Where did it connect?
Destination IP, port and domain from the HTTP Host header

How did it resolve?
DNS resolver used, returned address, response source and TTL

Was encryption expected?
Is the domain normally HTTPS-only or protected by HSTS?

What was exposed?
POST bodies, cookies, authentication tokens or personal information

What happened afterward?
Did the attacker connect to the real domain over TLS?

What is the scope?
Did other endpoints resolve the domain to or connect to the same IP?
```
