# DHCP 


DHCP process: 
```
Discover = I need an IP. Any DHCP server?
Offer = I can offer this IP and network settings
Request = I want this IP / I want to renew this IP.
ACK = Approved.
Inform = I already have an IP; give me network options.
```


```
DHCP Request = good for identifying the client
DHCP ACK = good for confirming what was assigned
DHCP NAK = good for seeing denied/failed DHCP attempts
```

# How does DHCP work? how does it flow from traffic
# 1 - **Uses a broadcast address to find the DHCP server****
--------------------------------------------------------------------------
2 instances when a host joins a network
1. It doesn't have an IP 
2. It already has so remembered/configured IP information

Case #1: It doesn't have an IP 
Source: 0.0.0.0
Destination: 255.255.255.255
MAC: ff:ff:ff:ff:ff:ff

UDP: src: 67 dst: 68

* It broadcasts it since it's basically looking for a DHCP server 
	"Is there any DHCP server that can give me an IP address"

Case #2: If it does have IP memory
* May remember the lease and try to get that IP again, so it may send a request instead of a discover 
# 2 - Server offers the network settings 
--------------------------------------------------------------------------
```
Offered IP: 192.168.1.25
Subnet mask: 255.255.255.0
Default gateway: 192.168.1.1
DNS server: 192.168.1.1
Lease time: 24 hours
DHCP server ID: 192.168.1.1
```

**Traffic-wise**: 
```
Source IP: 192.168.1.1
Destination IP: 255.255.255.255 or offered/client-related address

Source MAC: DHCP server MAC
Destination MAC: client MAC or ff:ff:ff:ff:ff:ff
```

It uses broadcast since it might still not be fully configured to receive a unicast traffic yet 

# 3 - Client responds, "I want to use this" Request  
--------------------------------------------------------------------------
```
dhcp.option.dhcp == 3
```

```
Client sends request:
“I choose 192.168.1.25 from server 192.168.1.1.”
```
**Traffic-wise**
```
Source IP: 0.0.0.0
Destination IP: 255.255.255.255

Source MAC: client MAC
Destination MAC: ff:ff:ff:ff:ff:ff

UDP:
68 -> 67
```

Why is it using broadcast again? Because it's specifying which server configuration the host accepted.

This is the useful part since it identifies: 
```
Option 12: Hostname
Option 50: Requested IP address
Option 54: DHCP server identifier
Option 61: Client identifier / client MAC-like ID
```

If multiple servers offer this happens: 
```
DHCP Server A offers: 192.168.1.25
DHCP Server B offers: 192.168.1.80

Client chooses Server A.

Client broadcasts DHCP Request:
Requested IP: 192.168.1.25
DHCP Server Identifier: Server A
```

And the unchosen servers withdraw their offered addresses.

# 4 - ACK, approved for usage 
--------------------------------------------------------------------------
```
dhcp.option.dhcp == 5
```
The client configures its network settings given by the DHCP server which can look like this template: 
```
Assigned IP address
Subnet mask
Default gateway/router
DNS server
Domain name
Lease time
Renewal time
Rebinding time
DHCP server identifier
```


**REQ AND ACK ARE IMPORTANT BECAUSE IT PROVIDES THE MOST INFORMATION**:
```
Request:
Who is the client?
What hostname/client ID/MAC is it using?
What IP is it requesting?

ACK:
Was the request accepted?
What IP/config did the server actually assign?
What domain/DNS/gateway/lease details were given?
```

And it **helps identify which hosts are associated with a malicious activity**

```
Which device/hostname had 192.168.1.25 at that time?
What MAC address was tied to it?
What DHCP server approved it?
What domain/network config did it receive?
```
since it provides: 
```
DHCP Request:
Hostname: DESKTOP-JOHN
MAC: aa:bb:cc:dd:ee:ff
Requested IP: 192.168.1.25

DHCP ACK:
Server approved 192.168.1.25
Domain: corp.local
Lease time: 8 hours
```

# 5- Inform and NACK 
--------------------------------------------------------------------------
	1. Inform is used when: usually when a device has a static IP
```
“I already have an IP. Give me extra settings.”
```

	2. NACK
```
“No, you cannot use that requested IP/config.”
```
```
Client requested an IP that is not valid on this network
Client moved to a different subnet
The lease is expired or no longer valid
The IP is already in use or not available
Wrong DHCP server for that address
Policy/configuration issue
```
Wireshark: 
```
dhcp.option.dhcp == 6
```
Useful field: 
```
Option 56 = Message
```
can be tied to: 
```
Many NAKs to one client
Many clients getting NAKs
A client repeatedly requesting strange IPs
NAKs from an unexpected DHCP server
```

# NetBIOS maps IP <---> Hostname

NetBIOS is another “host identity” source, especially in Windows-heavy networks. 
Used for: 
```
computer names
workgroup/domain names
file sharing discovery
local name resolution
```
NBNS and UDP port 137 filters can help investigate name-resolution traffic. 
```
Who has this NetBIOS name?
What IP is associated with this Windows hostname?
What names is this host announcing?
```
```
UDP 137 = NetBIOS Name Service
UDP 138 = NetBIOS Datagram Service
TCP 139 = NetBIOS Session Service
```

NetBIOS is a name resolution within the local network.
It answers, "Who is FILSERVER"
NetBIOS will respond, "FILSERVER is at 192.168.10.1"

```
NBNS query = “Who is this name?”
nbns.flags.response == 0

NBNS response = “This name is at this IP.”
nbns.flags.response == 1
```

Reveals names and who is searching for them


At a high level, Kerberos is used to prove:

```
“This user/computer is who they claim to be.”
```

```
Instead of sending your password to every service,
you authenticate to the domain controller,
then get tickets that let you access services.
```
```
1. User logs in.
2. Client asks the Domain Controller for a ticket-granting ticket.
3. Domain Controller replies with a TGT.
4. Client uses TGT to request a service ticket.
5. Client presents service ticket to the target service.
```
Wireshark filter: 
kerberos (tcp/udp 88)
It can reveal:

```
username
domain/realm
client hostname sometimes
service being requested
domain controller involved
client IP address
```

Other fields:

```
kerberos.realm
```

Domain/realm, like:

```
CORP.LOCAL
EXAMPLE.ORG
```


```
kerberos.SNameString
```

Service name being requested.

Example:

```
krbtgt
cifs
ldap
http
host
```

```
kerberos.SNameString == "krbtgt"
```

is looking for tickets involving the ticket-granting service.

Yes. In Windows Active Directory/Kerberos context, an account name ending with `$` usually means it is a **computer/machine account**.

```
xp1$  = computer/machine account
u1    = user account
```

# CHEAT SHEET UNDERSTANDING

```
DHCP maps IP -> device/MAC/lease.
NBNS maps IP/name behavior -> local hostname clues.
Kerberos maps activity -> domain user/computer identity.
```
