**Brute force activity**
Example: 
Imagine you are a SOC L1 analyst on shift, and you’ve just received an alert about a possible brute-force attack targeting a WordPress login page. To investigate, we recommend starting by 
1. identifying the login page URL (e.g., /wp-login.php) 
2. and filtering for POST requests.
3
Brute-force activity involves many repeated attempts, so set a threshold like count > 25 during 5 mins. Group the results by clientip to pinpoint the source of the activity. Other fields, such as user-agent, can also provide useful context. Below is the ready query.
```
index=* method=POST uri_path="/wp-login.php" ( - an index is a storage collection for events, rather than a source itself)
| bin _time span=5m
| stats values(referer_domain) as referer_domain
        values(status) as status
        values(useragent) as UserAgent
        values(uri_path) as uri_path
        count by clientip _time
| where count > 25
| table referer_domain clientip UserAgent uri_path count status
```
- **`_time`** is the event’s timestamp.
- **`bin`** places numerical values—including timestamps—into buckets.
- **`span=5m`** makes each bucket five minutes wide.

So each bucket will contain events that are the span of 5 minutes 
So these give the events the same time interval

| Event | Original `_time` | `_time` after `bin` |
| ----- | ---------------- | ------------------- |
| A     | 10:01            | **10:00**           |
| B     | 10:03            | **10:00**           |
| C     | 10:04            | **10:00**           |
| D     | 10:06            | **10:05**           |

| stats values(referer_domain) as referer_domain
        values(status) as status
        values(useragent) as UserAgent
        values(uri_path) as uri_path
        count by clientip _time
